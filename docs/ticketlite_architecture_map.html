TicketLite Architecture Map
TicketLite · DevSecOps microservice lab

Application architecture ของแต่ละ domain

สรุปการเลือกสถาปัตยกรรมภายใน service ของ TicketLite ว่าแต่ละ domain ใช้แบบไหน เพราะอะไร และโครงโฟลเดอร์หน้าตาเป็นอย่างไร ระบบโดยรวมเป็น microservices + event-driven ผ่าน NATS JetStream โดยมี APISIX เป็น gateway

อัปเดต 8 ต.ค. 2026Go · TypeScriptmonorepo

สามคำถามที่ใช้เลือก

Q1 · กฎมี state transition หรือ invariant ที่ซับซ้อนไหม ถ้ามี กฎควรมีบ้านของตัวเองใน domain layer
Q2 · infraมี infra ที่อยากสลับหรือ fake ได้ไหม ถ้ามี port กับ adapter คุ้มค่า
Q3 · งานส่งต่องานหลักคืออ่าน แปล หรือส่งต่อใช่ไหม ถ้าใช่ ชั้นที่ซ้อนกันเป็นแค่พิธีกรรม

รายละเอียด

แต่ละ domain

booking

HexagonalGo

ตอบ "ใช่" ทั้ง Q1 และ Q2 ชัดเจน Booking aggregate มี status flow PENDING_PAYMENT → CONFIRMED / EXPIRED และกฎเรื่องเวลา hold ทางเข้ามีสองทาง (HTTP และ NATS consumer) ส่วนทางออกมี Postgres, Redis, NATS และ catalog โปรเจคตัวอย่างสร้างไว้แล้ว

โครงโฟลเดอร์
services/booking/
├── cmd/server/main.go
├── internal/
│   ├── domain/       booking, events, errors
│   ├── app/          use case + ports.go
│   ├── adapters/
│   │   ├── httpapi/     driving
│   │   ├── messaging/   driving + driven
│   │   ├── postgres/    driven
│   │   ├── redisstore/  driven (seat hold)
│   │   ├── catalog/     driven (gRPC client)
│   │   └── idgen/
│   └── config/
└── migrations/
จุดสำคัญ
  • กฎอยู่ใน method ของ aggregate เช่น Confirm(), Expire()
  • app/ คือชั้น use case ทำหน้าที่ประสานงาน ไม่ตัดสินกฎ
  • Clock เป็น port เพื่อ test กรณีหมดเวลาได้
  • Redis hold ใช้ Lua script แบบ all-or-nothing
  • ดึง event ออกจาก aggregate ก่อน save
ยังไม่ทำ
  • Transactional outbox
  • Scheduler สำหรับ ExpireBooking
  • Optimistic locking (คอลัมน์ version)

payment

HexagonalGo

เป็น service ที่ hexagonal ให้ประโยชน์เห็นชัดที่สุด เพราะ PaymentProvider มี adapter สองตัวจริงตั้งแต่วันแรก และเป็นจุดอ่อนด้าน security มากที่สุดในระบบ การแยกการตรวจลายเซ็นไว้ใน adapter กับกฎสถานะไว้ใน domain ทำให้ review ง่าย

โครงโฟลเดอร์
services/payment/
├── cmd/server/main.go
├── internal/
│   ├── domain/       payment (state machine)
│   ├── app/          create, handle webhook, refund
│   └── adapters/
│       ├── httpapi/     REST + webhook endpoint
│       ├── provider/
│       │   ├── stripe/
│       │   └── mock/
│       ├── postgres/
│       └── messaging/   publish payment.succeeded
└── migrations/
จุดสำคัญ
  • state machine pending → succeeded / failed → refunded อยู่ใน domain
  • ตรวจลายเซ็น webhook ใน adapter ก่อนเข้าถึง core
  • webhook ต้อง idempotent ใช้ event id ของ provider กันการประมวลผลซ้ำ
  • ควรใช้ outbox ตั้งแต่ต้น เพราะ event payment.succeeded หายไม่ได้

catalog

Layered + repository interfaceGo

งานส่วนใหญ่คือจัดการ event, ที่นั่ง และราคา แล้วตอบ gRPC ให้ booking อ่าน กฎที่มีจริงวางใน service layer ได้โดยไม่ยุ่ง และได้เห็น layered กับ hexagonal อยู่คู่กันในระบบเดียวเพื่อเปรียบเทียบ

โครงโฟลเดอร์
services/catalog/
├── cmd/server/main.go
├── internal/
│   ├── grpcapi/      handler (proto ↔ model)
│   ├── service/      logic + กฎไม่กี่ข้อ
│   ├── repository/   interface + postgres impl
│   ├── model/
│   └── config/
└── migrations/
จุดสำคัญ
  • flow: grpcapi → service → repository → Postgres
  • repository เป็น interface เพื่อ test service ได้ด้วย fake
  • ตัวอย่างกฎ: ลด capacity ต่ำกว่าจำนวนที่ขายไปแล้วไม่ได้
ทางย้ายในอนาคต

ถ้ามีกฎเพิ่ม เช่น pricing tier หรือเปิดขายเป็นรอบ ให้ดึงกฎจาก service/ ลง domain/ ย้ายไป hexagonal ได้ไม่ยากเพราะ repository เป็น interface อยู่แล้ว

notification

Vertical sliceGo

ทำงานเป็น consumer เป็นหลัก แต่ละ handler แทบไม่แชร์ logic กัน จึงแบ่งโฟลเดอร์ตาม event ส่วนที่แชร์มีแค่ช่องทางการส่ง ซึ่งเป็น interface เล็กๆ ตัวเดียว

โครงโฟลเดอร์
services/notification/
├── cmd/worker/main.go
├── internal/
│   ├── onbookingconfirmed/   ส่งตั๋ว
│   ├── onbookingexpired/     แจ้งหมดเวลา
│   ├── sender/
│   │   ├── sender.go         interface Sender
│   │   └── email/            implementation
│   └── config/
จุดสำคัญ
  • หนึ่ง slice = consume event + เตรียมข้อความ + เรียก Sender
  • Sender fake ได้ตอน test และเพิ่มช่องทางใหม่ภายหลังได้
  • consumer ต้อง idempotent เพราะ JetStream ส่งแบบ at-least-once

partner-api

Layered แบบบางGo

ไม่มีกฎธุรกิจเป็นของตัวเอง รับ request ในรูปแบบของ partner แปลง แล้วเรียก booking หรือ catalog ต่อ ถ้าใส่ domain layer จะเหลือแค่ struct ที่ copy field ไปมา

โครงโฟลเดอร์
services/partner-api/
├── cmd/server/main.go
├── internal/
│   ├── handler/   รับ + validate + แปลง contract
│   ├── client/    booking, catalog
│   └── config/
จุดสำคัญ
  • flow: handler → client
  • งานหลักอยู่ที่ security: API key, rate limit ที่ APISIX, input validation
  • contract ของ partner ต้อง version แยกจาก API ภายใน

GraphQL BFF

Feature moduleTypeScript

เป็นแนว API Composition ไม่มี domain แต่ละ module รวม schema, resolver และ DataLoader ของ feature นั้นไว้ด้วยกัน

โครงโฟลเดอร์
apps/bff/src/
├── modules/
│   ├── events/
│   │   ├── schema.graphql
│   │   ├── resolvers.ts
│   │   └── loaders.ts
│   └── bookings/
├── clients/     booking, catalog, payment
└── server.ts
จุดสำคัญ
  • DataLoader ลดปัญหา N+1 เมื่อรวมข้อมูลหลาย service
  • ถ้าหน้าใดช้าเพราะ join เยอะ ค่อยพิจารณา read model แบบ CQRS
กฎร่วม

สิ่งที่ต้องเหมือนกันทุก service

ภายในต่างกันได้ แต่โครงด้านนอกต้องเหมือนกัน เพื่อให้ CI และฝั่ง ops ไม่ต้องสนใจว่าข้างในเป็นแบบไหน

  • cmd/<binary>/main.go เป็น composition root ที่เดียวที่รู้จักทุก dependency
  • internal/config, รูปแบบการ log และการตั้ง OpenTelemetry ใช้ร่วมจาก libs/go
  • /healthz, graceful shutdown, Dockerfile แบบ distroless และ pipeline แบบเดียวกัน
  • .golangci.yml ชุดเดียวกัน เพิ่มกฎ depguard เฉพาะ service ที่เป็น hexagonal
  • ห้ามแชร์ domain model ข้าม service ถ้าต้องแชร์ event payload ให้ใช้ schema ที่ version ไว้
Hexagonal

ทิศทาง import ที่ต้องรักษา

cmd→adapters→app→domain

domain ใช้ได้แค่ stdlib, app import ได้แค่ domain, ส่วน cmd เป็นที่เดียวที่รู้จัก adapter ตัวจริง บังคับด้วย depguard ใน CI

ข้อมูลรูปร่างไหน อยู่ที่ ใครรู้จัก
request / response struct (มี json tag) adapters/httpapi/dto.go HTTP adapter
input ของ use case app/<usecase>.go app และ adapter ที่เรียก
aggregate domain/ ทุกชั้น
row struct ของ DB adapters/postgres/ Postgres adapter
