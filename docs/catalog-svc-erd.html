Catalog Service ERD

catalog service เก็บข้อมูลของ "สิ่งที่ขาย" ทั้งหมด คืองานอะไร จัดที่ไหน มีกี่รอบ นั่งตรงไหนได้บ้าง และราคาเท่าไร หน้านี้อธิบายว่าแต่ละตารางเก็บอะไร และเชื่อมกันอย่างไร

9 ตาราง2 กลุ่มข้อมูลหลัก7 เส้นเชื่อมแบบ FKPostgreSQL บน CNPG

ภาพรวมใน 1 นาที

กลุ่มสถานที่

บอกว่าสถานที่มีหน้าตาอย่างไร มีโซนอะไร และมีเก้าอี้ตัวไหนบ้าง ข้อมูลกลุ่มนี้ไม่รู้เรื่องราคา และใช้ซ้ำได้กับหลายงาน

venues → seat_maps → seat_map_sections → seat_map_seats

กลุ่มงาน

บอกว่างานชื่ออะไร เปิดขายเมื่อไร มีรอบไหนบ้าง และโซนไหนราคาเท่าไร กลุ่มนี้หยิบผังที่นั่งจากกลุ่มสถานที่มาใช้

events → showtimes, ticket_tiers → tier_sections

กล่องจดหมายขาออก

ทุกครั้งที่งานเปลี่ยนสถานะ เช่น เปิดขายหรือยกเลิก จะมีจดหมายหนึ่งฉบับลงในกล่องนี้ แล้วมีตัวส่งเอาไปแจ้ง service อื่น

outbox

เทียบให้เห็นภาพ: กลุ่มสถานที่คือแบบแปลนโรงละคร ส่วนกลุ่มงานคือใบประกาศขายตั๋วที่เอาแบบแปลนนั้นมาระบายสีว่าโซนไหนราคาเท่าไร

ศัพท์ที่ใช้ในหน้านี้

PK
รหัสประจำแถว ห้ามซ้ำ เหมือนเลขบัตรประชาชนของข้อมูลแถวนั้น
FK
ช่องที่เก็บรหัสของแถวในอีกตาราง เพื่อบอกว่า "แถวนี้เป็นของใคร" database จะไม่ยอมให้ใส่รหัสที่ไม่มีอยู่จริง
1 : N
หนึ่งต่อหลาย เช่น งาน 1 งานมีได้หลายรอบ แต่รอบ 1 รอบเป็นของงานเดียว ในภาพ เลข 1 อยู่ฝั่งแม่ ตัว N อยู่ฝั่งลูก
ตารางแม่ / ลูก
ตารางลูกคือตารางที่มี FK ชี้ไปหาตารางแม่ เช่น showtimes เป็นลูกของ events
DRAFT / LOCKED
DRAFT คือยังร่างอยู่ แก้ได้ทุกอย่าง LOCKED คือถูกล็อกแล้ว แก้ไม่ได้อีก
created_* / updated_*
คอลัมน์บันทึกว่าใครสร้างและใครแก้ล่าสุด เมื่อไร มี 4 ช่อง: created_at, created_by, updated_at, updated_by มีเฉพาะตารางที่ผู้ใช้แก้โดยตรง เวลาทั้งสองช่อง database ใส่ให้เอง (updated_at ใช้ trigger) ส่วนผู้สร้างและผู้แก้ service ต้องส่งมาจาก token ของผู้ใช้
version
ตัวเลขที่บวกเพิ่มทุกครั้งที่ข้อมูลงานเปลี่ยน ใช้เช็กว่าข้อมูลที่ถืออยู่ใหม่หรือเก่า

ภาพความเชื่อมโยง

แต่ละกล่องคือหนึ่งตาราง เส้นทึบคือการเชื่อมที่ database ตรวจให้ (FK) เส้นประสีแดงคือการเชื่อมที่ database ไม่ได้ตรวจ แต่ระบบตรวจเองในจังหวะอื่น

กลุ่มสถานที่ กลุ่มงาน กล่องจดหมายขาออก เชื่อมแบบ FK เชื่อมแบบไม่มี FK UQ = ค่าห้ามซ้ำ

ตัวอย่าง: เก้าอี้ A-12 ราคาเท่าไร

ลองถามคำถามง่ายๆ ว่า "เก้าอี้ A-12 ในรอบคืนวันเสาร์ ราคาเท่าไร" ระบบต้องเดินผ่านตารางตามลำดับนี้ถึงจะตอบได้

  1. 1showtimesหารอบคืนวันเสาร์ ได้คำตอบว่ารอบนี้เป็นของงานคอนเสิร์ต X และใช้ผังที่นั่งแบบที่ 2 ของ Hall A
  2. 2seat_mapsเปิดผังแบบที่ 2 ผังนี้ถูกล็อกแล้ว ไม่มีใครแก้ได้ระหว่างขาย
  3. 3seat_map_seatsในผังนี้ A-12 คือแถว A เก้าอี้ตัวที่ 12 อยู่ในโซน A
  4. 4tier_sectionsงานคอนเสิร์ต X กำหนดว่าโซน A เป็นระดับ VIP
  5. 5ticket_tiersVIP ของงานนี้ราคา 5,000 บาท
  6. 6eventsเช็กว่างานกำลังเปิดขายอยู่จริง ถ้ายังไม่เปิดหรือยกเลิกไปแล้วจะขายไม่ได้

สังเกตว่าราคาไม่ได้ติดอยู่กับเก้าอี้ แต่มาจากการจับคู่ "โซน" กับ "ระดับราคา" ของแต่ละงาน งานอื่นที่ใช้ผังเดียวกันจึงตั้งราคาโซน A ต่างไปได้

แต่ละตารางเก็บอะไร

กลุ่มสถานที่

สร้างครั้งเดียว ใช้ได้หลายงาน

venues

สถานที่จัดงาน

เก็บชื่อสถานที่ ที่อยู่ และเขตเวลา (เอาไว้แสดงเวลารอบให้ถูก)

ตัวอย่าง
Hall A, ถนนพระราม 9, Asia/Bangkok
เชื่อมกับ
หนึ่งสถานที่มีผังที่นั่งได้หลายแบบ (seat_maps)
กฎสำคัญ
สถานที่เป็นของ organizer คนที่สร้าง คนอื่นแก้หรือเอาไปใช้ในงานของตัวเองไม่ได้

seat_maps

แบบผังที่นั่ง

ผังที่นั่งของสถานที่ แต่ละแบบมีเลขรุ่น เช่น ปีนี้จัดเวทีกลาง ปีหน้าย้ายเวทีไปด้านหน้า ก็เป็นผังแบบที่ 1 กับแบบที่ 2

ตัวอย่าง
Hall A แบบที่ 2, สถานะ LOCKED
เชื่อมกับ
เป็นของ venues หนึ่งแห่ง ข้างในแบ่งเป็นโซน (seat_map_sections) และถูกรอบการแสดง (showtimes) หยิบไปใช้
กฎสำคัญ
พองานที่ใช้ผังนี้ประกาศขาย ผังจะถูกล็อกทันที ห้ามเพิ่ม ลบ หรือย้ายเก้าอี้ ถ้าอยากเปลี่ยนต้องคัดลอกเป็นแบบใหม่ เพื่อให้ตั๋วที่ขายไปแล้วยังชี้ไปที่เก้าอี้ที่มีอยู่จริงเสมอ

seat_map_sections

โซนในผัง

แบ่งผังเป็นโซน เช่น โซน A ด้านหน้า โซน C ด้านหลัง โซนคือหน่วยที่ใช้ตั้งราคา

ตัวอย่าง
A (ด้านหน้าซ้าย), B (ด้านหน้าขวา), C, D
เชื่อมกับ
อยู่ในผัง (seat_maps) หนึ่งแบบ ข้างในมีเก้าอี้หลายตัว (seat_map_seats)
กฎสำคัญ
ในผังเดียวกันชื่อโซนห้ามซ้ำ แต่ผังคนละแบบมีโซน A เหมือนกันได้

seat_map_seats

เก้าอี้ทุกตัว

เก้าอี้แต่ละตัวในผัง มีรหัส (เช่น A-12) ไว้ให้ระบบใช้ และมีแถวกับเลขที่นั่งไว้ให้คนอ่าน ตารางนี้มีข้อมูลเยอะที่สุด ผังหนึ่งมีได้หลายพันตัว

ตัวอย่าง
A-12 = โซน A, แถว A, ที่นั่งที่ 12
เชื่อมกับ
อยู่ในโซน (seat_map_sections) หนึ่งโซน และโซนนั้นต้องอยู่ในผังเดียวกันกับเก้าอี้
ใช้ต่อที่
booking service คัดลอกรายการเก้าอี้ไปตอนเปิดขาย เพื่อเอาไปนับว่าตัวไหนว่าง ตัวไหนขายแล้ว
กฎสำคัญ
ในโซนเดียวกัน แถวเดียวกันมีที่นั่งเลขซ้ำกันไม่ได้ แต่ต่างโซนมี "แถว A ที่ 12" ซ้ำกันได้ เหมือนสถานที่จริงที่หลายโซนใช้ชื่อแถวชุดเดียวกัน
กลุ่มงาน

ข้อมูลของการขายแต่ละครั้ง ทุกการเปลี่ยนแปลงในกลุ่มนี้ทำให้ version ของงานเพิ่มขึ้น 1

events

งาน (ตารางหลัก)

หนึ่งแถวคือหนึ่งงาน เก็บชื่องาน สถานะ ช่วงเวลาเปิดขาย สกุลเงิน และจำนวนตั๋วสูงสุดที่คนหนึ่งซื้อได้ต่อรอบ

ตัวอย่าง
คอนเสิร์ต X, เปิดขาย 1 พ.ย. ปิดขาย 30 พ.ย., THB, คนละไม่เกิน 4 ใบ
เชื่อมกับ
มีรอบหลายรอบ (showtimes) และมีระดับราคาหลายระดับ (ticket_tiers)
สถานะ
ร่าง → ประกาศแล้ว → เปิดขาย → ขายหมด / ปิดขาย → (ยกเลิกได้ทุกช่วง) เดินย้อนกลับไม่ได้
กฎสำคัญ
  • ช่วงเปิดขาย สกุลเงิน และจำนวนตั๋วต่อคนแก้ได้ตอนเป็นร่างเท่านั้น
  • เจ้าของงานเปลี่ยนไม่ได้
  • ยกเลิกแล้วแก้อะไรไม่ได้อีก และลบได้เฉพาะงานที่ยังเป็นร่าง

showtimes

รอบการแสดง

แต่ละรอบของงาน บอกวันเวลา สถานที่ และผังที่นั่งที่ใช้ เป็นตารางเดียวที่เชื่อมกลุ่มงานกับกลุ่มสถานที่เข้าหากัน

ตัวอย่าง
คืนวันศุกร์ 19:00 กับคืนวันเสาร์ 19:00 ที่ Hall A ผังแบบที่ 2
เชื่อมกับ
เป็นของงาน (events) หนึ่งงาน และใช้ผัง (seat_maps) หนึ่งแบบ
กฎสำคัญ
  • ผังที่เลือกต้องเป็นของสถานที่เดียวกับรอบ database ตรวจให้
  • เพิ่มหรือลบรอบได้ตอนเป็นร่างเท่านั้น หลังประกาศแล้วทำได้แค่เลื่อนเวลา
  • เวลาใหม่ต้องอยู่ในอนาคต และไม่ก่อนวันปิดขาย

ticket_tiers

ระดับราคา

ระดับราคาของงาน เช่น VIP กับ Regular ราคาใช้เท่ากันทุกรอบของงานนั้น เก็บเป็นสตางค์ (5,000 บาท เก็บเป็น 500000) เพื่อไม่ให้มีปัญหาทศนิยม

ตัวอย่าง
VIP 5,000 บาท, REG 2,000 บาท
เชื่อมกับ
เป็นของงาน (events) และจับคู่กับโซนผ่าน tier_sections
กฎสำคัญ
แก้ราคาได้จนถึงก่อนเปิดขาย พอเปิดขายแล้วราคาถูกล็อก คนที่จองไปแล้วจะจ่ายราคาที่เห็นตอนจองเสมอ เพราะ booking จดราคาเก็บไว้เอง
ไม่มี
จำนวนตั๋วของแต่ละระดับ เพราะนับได้จากจำนวนเก้าอี้ในโซนที่จับคู่ไว้

tier_sections

จับคู่โซนกับราคา

ตารางสั้นๆ ที่บอกว่าโซนไหนได้ราคาระดับไหน เช่น "โซน A และ B เป็น VIP" เก้าอี้ทุกตัวจึงมีราคาโดยไม่ต้องตั้งทีละตัว

ตัวอย่าง
A → VIP, B → VIP, C → REG, D → REG
เชื่อมกับ
ชี้ไปที่ระดับราคา (ticket_tiers) และชี้ไปที่ชื่อโซน (seat_map_sections) โดยฝั่งโซนไม่มี FK เพราะงานหนึ่งอาจมีหลายรอบที่ใช้ผังต่างกัน
กฎสำคัญ
  • หนึ่งโซนได้ราคาเดียวในงานหนึ่ง
  • ก่อนประกาศงาน ทุกโซนต้องมีราคา และทุกระดับราคาต้องมีโซน ไม่อย่างนั้นประกาศไม่ผ่าน
ทำไมอยู่กลุ่มงาน
ผังเดียวกันใช้ได้หลายงาน งานหนึ่งอาจให้โซน B เป็น VIP อีกงานให้เป็น Regular การจับคู่จึงต้องเป็นของงาน
กล่องจดหมายขาออก

ไม่ได้เก็บข้อมูลงาน เป็นทางส่งข่าวไปหา service อื่น

outbox

จดหมายที่รอส่ง

ทุกครั้งที่งานถูกประกาศ เปิดขาย เลื่อนรอบ หรือยกเลิก ระบบจะเขียนจดหมายหนึ่งฉบับลงตารางนี้ พร้อมกับการเปลี่ยนข้อมูลงาน แล้วมีตัวส่งคอยหยิบจดหมายไปส่งเข้า NATS ให้ booking, partner-api และ notification

ทำไมต้องมี
ถ้าเปลี่ยนข้อมูลงานแล้วส่งข่าวตรงๆ อาจเกิดกรณีที่ข้อมูลเปลี่ยนแล้วแต่ข่าวส่งไม่ถึง เช่น งานถูกยกเลิกแต่ booking ยังขายต่อ การเขียนลงตารางพร้อมกันทำให้ "ข้อมูลเปลี่ยน" กับ "มีข่าวรอส่ง" เกิดคู่กันเสมอ
เชื่อมกับ
จดหมายแต่ละฉบับระบุว่าเป็นของงานไหน (aggregate_id) แต่ไม่มี FK เพราะต้องเก็บไว้แม้งานจะถูกลบ
ประเภทจดหมาย
EventPublished, SalesOpened, ShowtimeRescheduled, EventCancelled
ข้อควรรู้
ข่าวอาจถูกส่งซ้ำได้ แต่ไม่หาย ฝั่งที่รับจึงต้องเช็กว่าเคยรับฉบับนี้แล้วหรือยัง
ยังขาด
งานลบจดหมายที่ส่งไปนานแล้ว เช่น เกิน 7 วัน ไม่อย่างนั้นตารางจะโตไปเรื่อยๆ

เส้นเชื่อมทั้งหมด

ตารางนี้สรุปเส้นทึบทุกเส้นในภาพ ช่อง "ถ้าลบแม่" บอกว่าถ้าลบแถวในตารางแม่ แถวลูกจะเป็นอย่างไร

ลูก → แม่ แบบ ถ้าลบแม่ อ่านว่า
seat_maps → venues N : 1 ห้ามลบ ถ้ายังมีผัง สถานที่หนึ่งมีผังได้หลายแบบ
seat_map_sections → seat_maps N : 1 โซนหายตาม ผังหนึ่งมีหลายโซน (ผังที่ล็อกแล้วลบไม่ได้อยู่แล้ว)
seat_map_seats → seat_map_sections N : 1 เก้าอี้หายตาม โซนหนึ่งมีเก้าอี้หลายตัว และเก้าอี้ต้องอยู่ในโซนของผังเดียวกัน
showtimes → events N : 1 รอบหายตาม งานหนึ่งมีหลายรอบ ลบงานได้เฉพาะตอนเป็นร่าง
showtimes → seat_maps N : 1 ห้ามลบ ถ้ามีรอบใช้อยู่ ผังหนึ่งถูกหลายรอบใช้ได้ และผังต้องเป็นของสถานที่เดียวกับรอบ
ticket_tiers → events N : 1 ระดับราคาหายตาม งานหนึ่งมีหลายระดับราคา
tier_sections → ticket_tiers N : 1 การจับคู่หายตาม ระดับราคาหนึ่งครอบได้หลายโซน

เส้นประ: เชื่อมกันแต่ไม่มี FK

เส้น ทำไมไม่ใช้ FK ระบบตรวจอย่างไรแทน
tier_sections ⇢ seat_map_sections งานหนึ่งอาจมีหลายรอบที่ใช้ผังต่างกัน ชื่อโซนเดียวจึงต้องชี้ไปได้หลายผังพร้อมกัน ซึ่ง FK ทำไม่ได้ ตอนกดประกาศงาน ระบบเช็กว่าทุกโซนในทุกผังมีราคาครบ ถ้าไม่ครบจะบอกว่าโซนไหนยังขาด
outbox ⇢ events จดหมายเป็นบันทึกว่าเกิดอะไรขึ้นแล้ว ต้องเก็บไว้แม้งานจะถูกลบ จดหมายถูกเขียนพร้อมกับการเปลี่ยนข้อมูลงานเสมอ จึงไม่มีจดหมายของงานที่ไม่มีอยู่จริง

booking service เอาอะไรไปจาก catalog

แต่ละ service มี database ของตัวเอง booking จึงเชื่อมกับตารางของ catalog ตรงๆ ไม่ได้ ใช้วิธีคัดลอกข้อมูลที่ต้องใช้ไปเก็บเอง โดยได้รับผ่านจดหมาย (event) หรือถามตรง (gRPC)

booking เก็บ เอามาจาก ได้มาตอนไหน
รอบการแสดง วันเวลา สถานที่ showtimes จดหมาย SalesOpened ตอนเปิดขาย และ ShowtimeRescheduled ตอนเลื่อนรอบ
จำนวนตั๋วสูงสุดต่อคน events จดหมาย SalesOpened
รุ่นของข้อมูล (catalog_version) events.version ทุกจดหมาย ใช้ทิ้งจดหมายเก่าที่มาถึงช้า
งานถูกยกเลิก events จดหมาย EventCancelled
รายการเก้าอี้และระดับราคาของแต่ละตัว seat_map_seats + tier_sections ถาม catalog ตรง (ListShowtimeSeats) หลังได้จดหมายเปิดขาย
ราคาตั๋วในใบจอง ticket_tiers ถาม catalog ตรง (GetTierPrices) ตอนลูกค้ากดจอง
วันปิดขาย ยังไม่มี ต้องเพิ่ม events.sales_close_at จดหมาย SalesOpened เพราะตอนปิดขายไม่มีจดหมายแจ้ง booking จึงต้องดูวันเอง

กฎที่ database บังคับเอง

นอกจากเส้นเชื่อม database ยังมีตัวเฝ้า (trigger) คอยปฏิเสธการแก้ข้อมูลที่ผิดกฎ ถึงโค้ดฝั่ง service จะลืมเช็ก ข้อมูลก็ยังไม่พัง

กลุ่ม กฎ ชื่อ error ที่ได้
สถานที่ ผังที่ล็อกแล้ว ห้ามเพิ่ม ลบ หรือแก้โซนและเก้าอี้ ห้ามปลดล็อก และห้ามลบผัง seat_map_locked
งาน สถานะเดินได้ตามลำดับเท่านั้น เช่น เปิดขายแล้วจะกลับไปเป็นร่างไม่ได้ event_invalid_transition
งาน เจ้าของงานเปลี่ยนไม่ได้ event_owner_immutable
งาน หลังประกาศแล้ว ห้ามเพิ่มหรือลบรอบ ระดับราคา และการจับคู่โซน ห้ามแก้ช่วงเปิดขาย และห้ามลบงาน event_structure_locked
งาน เปิดขายแล้วห้ามแก้ราคา tier_price_locked
งาน งานที่ยกเลิกแล้ว แก้อะไรไม่ได้อีก ทั้งตัวงานและรอบ event_cancelled

เหตุผลการออกแบบ

ส่วนนี้บันทึกว่าทำไม schema ถึงออกมาหน้าตาแบบนี้ สำหรับคนที่จะเขียน migration หรือแก้ตารางต่อ กลุ่มสถานที่ทำเป็น migration แล้ว (00001–00005) กลุ่มงานทำแล้ว events และ showtimes (00006–00007) ส่วนตารางอื่นของกลุ่มงานและ outbox ยังเป็นแบบร่าง

หลักที่ใช้กับทุกตาราง

เรื่อง ทำแบบนี้ เพราะ
PK แบบ uuid DEFAULT uuidv7() v7 ขึ้นต้นด้วยเวลา ค่าใหม่ต่อท้าย index เสมอ ส่วน v4 สุ่มกระจายทำให้ B-tree แตกหน้าบ่อย (uuidv7() มีใน Postgres 18)
ชนิดข้อความ text + CHECK ใน Postgres varchar(n) เก็บและเร็วเท่า text ต่างแค่จำกัดความยาว แต่ลดความยาวทีหลังต้องล็อกตาราง ส่วน CHECK เปลี่ยนได้ด้วย NOT VALID + VALIDATE ไม่ใช้ char(n) เพราะเติมช่องว่างจนเปรียบเทียบค่าเพี้ยน
ค่าที่มีให้เลือก (status) text + CHECK (… IN (…)) ENUM เพิ่มค่าได้แต่ลบหรือเปลี่ยนชื่อไม่ได้ CHECK ลบแล้วสร้างใหม่ได้ใน migration เดียว
ใส่ CHECK ที่ไหน เฉพาะช่องที่ระบบอื่นใช้ต่อ เช่นรหัสโซนและรหัสเก้าอี้ที่ booking คัดลอกไป ส่วนช่องที่แสดงผลอย่างเดียว เช่นชื่อหรือที่อยู่ ให้ service ตรวจ
ค่าว่าง NOT NULL เป็นค่าเริ่มต้น ผ่อนให้ว่างได้ทีหลังง่าย แต่เพิ่ม NOT NULL ตอนมีข้อมูลแล้วต้องไล่เติมข้อมูลเก่าให้ครบก่อน
ใครสร้าง / แก้เมื่อไร created_* / updated_* เฉพาะตารางที่ผู้ใช้แก้โดยตรง เวลาให้ database ใส่เอง (updated_at ใช้ trigger BEFORE UPDATE เพราะต้องแก้แถวก่อนถูกเขียนลง disk) ส่วน *_by ไม่มี DEFAULT เพราะ service ต่อ DB ด้วย user เดียวเสมอ DB ไม่รู้ว่าผู้ใช้จริงคือใคร ถ้าลืมส่งจะ error ทันที ตารางลูกอย่างโซนและเก้าอี้ถูกแก้พร้อมผัง จึงดูที่ผังแทน
ถ้าลบแม่ CASCADE หรือ RESTRICT CASCADE เมื่อลูกเป็นส่วนหนึ่งของแม่และไม่มีความหมายถ้าอยู่ลำพัง (โซน เก้าอี้) RESTRICT เมื่อการลบอาจทำของที่อื่นพัง (ผังที่ showtime ใช้อยู่ ถ้าหายตั๋วที่ขายแล้วจะชี้ไปที่เก้าอี้ที่ไม่มีจริง)
Index สร้างเองเฉพาะที่ PK / UNIQUE ไม่ครอบ Postgres สร้าง index ให้แค่ PK กับ UNIQUE และ index หลายคอลัมน์ใช้กับ query ที่กรองด้วยคอลัมน์ต้นๆ ได้ จึงใช้แทน index ของ FK ได้ถ้าขึ้นต้นด้วยคอลัมน์เดียวกัน
ชื่อ constraint ตั้งเองเมื่อชื่ออัตโนมัติไม่สื่อ CHECK ที่อ้างหลายคอลัมน์ได้ชื่อ <table>_check อ่านจาก error แล้วไม่รู้ว่าผิดกฎข้อไหน และชื่อเกิน 63 ตัวอักษรจะถูกตัดท้าย
schema และสิทธิ์ schema catalog (ไม่มี public), migrator ทำ DDL, catalog_service ทำได้แค่ DML service ลบหรือแก้โครงตารางเองไม่ได้ และเข้า database ของ service อื่นไม่ได้ ตารางใหม่ที่ migrator สร้างได้สิทธิ์ DML ให้ service อัตโนมัติผ่าน ALTER DEFAULT PRIVILEGES

เหตุผลรายตาราง (กลุ่มสถานที่: venues, seat_maps, seat_map_sections, seat_map_seats)

ตาราง ทำแบบนี้ เพราะ
venues organizer_id text ไม่มี FK organizer อยู่ใน Keycloak คนละระบบ database ตรวจข้ามระบบไม่ได้ ใช้ text เผื่อเปลี่ยน identity provider ที่ id ไม่ใช่ UUID
venues timezone ไม่มี CHECK CHECK ต้องเป็นนิพจน์ immutable ค้นรายชื่อ timezone ของระบบไม่ได้ service จึงตรวจเองว่าเป็นชื่อที่มีอยู่จริง เช่น Asia/Bangkok
seat_maps UNIQUE (venue_id, version) เลขรุ่นห้ามซ้ำในสถานที่เดียวกัน และเพราะขึ้นต้นด้วย venue_id จึงไม่ต้องสร้าง index แยกให้ FK
seat_maps UNIQUE (seat_map_id, venue_id) ดูซ้ำซ้อนกับ PK แต่ showtimes ต้องทำ FK (seat_map_id, venue_id) เพื่อบังคับว่าผังเป็นของสถานที่เดียวกับรอบ และ Postgres กำหนดว่าปลายทางของ FK ต้องมี UNIQUE ตรงกันทุกคอลัมน์
seat_maps seat_maps_locked_at_matches_status LOCKED ⇔ มี locked_at กันข้อมูลขัดกันเอง เช่น LOCKED แต่ไม่รู้ว่าล็อกเมื่อไร
seat_map_sections PK (seat_map_id, section_code) แทน uuid โซนระบุตัวด้วย "ผังไหน + รหัสอะไร" อยู่แล้ว และทำให้เก้าอี้ทำ composite FK มาได้ ถ้าโซนใช้ uuid จะบังคับไม่ได้ว่าเก้าอี้อยู่ในโซนของผังเดียวกัน
seat_map_seats FK (seat_map_id, section_code) ไม่มี FK ไปหา seat_maps ตรงๆ ถ้า FK แค่ section_code จะชี้ไปโซน A ของผังไหนก็ได้ และไม่ต้อง FK ไปหาผังซ้ำ เพราะโซนต้องมีผังอยู่จริงอยู่แล้ว
seat_map_seats seat_map_seats_position_key UNIQUE รวม section_code สถานที่จริงมี "แถว A ที่ 12" ซ้ำกันในหลายโซน และเพราะขึ้นต้นด้วย (seat_map_id, section_code) จึงใช้เป็น index ของ FK ได้ ตอนลบโซน

เหตุผลรายตาราง (กลุ่มงาน: events, showtimes, ticket_tiers, tier_sections)

ตาราง ทำแบบนี้ เพราะ
events status CHECK แค่ค่าที่อนุญาต ลำดับการเปลี่ยนสถานะ (เดินหน้าอย่างเดียว) service เป็นคนตรวจ เพราะ CHECK เห็นแค่ค่าในแถวปัจจุบัน ไม่รู้ว่าก่อนหน้าเป็นสถานะอะไร
events currency text CHECK ^[A-Z]{3}$ char(3) เติมช่องว่างท้ายให้เองแบบเงียบๆ ส่วน CHECK ปฏิเสธ thb หรือ TH ทันที ตั๋วทุกระดับของงานใช้สกุลเงินเดียวกันจึงเก็บที่งาน
events events_sales_window_valid booking ใช้ช่วงเปิด–ปิดขายตัดสินว่ายังจองได้ไหม ถ้าปิดก่อนหรือพร้อมเปิด ลูกค้าจะจองนอกช่วงขายหรือไม่มีช่วงให้ขาย
events version service เป็นคนบวก ต้องบวกเมื่อ showtimes หรือ ticket_tiers เปลี่ยนด้วย ซึ่ง trigger ที่ events มองไม่เห็น booking ใช้ทิ้งจดหมายเก่า และ service ใช้กันแก้ทับกัน (WHERE version = ?)
events cancelled_* แยกจาก updated_* updated_* ถูกทับเมื่อแก้ครั้งถัดไป ส่วน events_cancelled_fields_match_status ใช้ num_nonnulls บังคับว่า CANCELLED ต้องมีครบ 3 ช่อง สถานะอื่นต้องว่างทั้ง 3 ช่อง
showtimes FK คู่ (seat_map_id, venue_id) → seat_maps บังคับว่าผังที่เลือกต้องเป็นของสถานที่เดียวกับรอบ ถ้า FK แค่ seat_map_id จะเก็บ venue ของ Hall A คู่กับผังของ Hall B ได้ ใช้ RESTRICT เพราะผังที่มีรอบใช้อยู่ห้ามหาย
showtimes venue_id ไม่มี FK ไป venues ตรงๆ FK คู่ด้านบนรับประกันแล้ว เพราะคู่นี้ต้องมีใน seat_maps ซึ่งมี FK ไป venues อีกที เก็บ venue_id ไว้ในรอบเพื่อไม่ต้อง JOIN ผังทุกครั้ง
showtimes showtimes_event_starts_at_key งานเดียวกันไม่มีสองรอบเริ่มพร้อมกัน และขึ้นต้นด้วย event_id จึงใช้เป็น index ของ FK ตอน CASCADE ลบงานได้
showtimes showtimes_seat_map_id_idx ตอนลบผัง Postgres ต้องหารอบที่ใช้ผังนี้เพื่อเช็ก RESTRICT ไม่มี index จะอ่านทั้งตาราง UNIQUE ด้านบนขึ้นต้นด้วย event_id จึงใช้แทนไม่ได้
showtimes "เวลาต้องอยู่ในอนาคต" ไม่ใช้ CHECK now() ไม่ใช่ immutable แถวที่ถูกวันนี้จะผิดในวันหน้า service ตรวจตอนสร้างหรือเลื่อนรอบ ส่วน CHECK ตรวจแค่ ends_at > starts_at

ยังไม่ได้ทำ

trigger seat_map_locked (ผังที่ล็อกแล้วห้ามแก้ผัง โซน และเก้าอี้) ต้องตรวจข้ามสามตาราง จึงแยกเป็น migration หลังสร้างครบทั้งสามตาราง
