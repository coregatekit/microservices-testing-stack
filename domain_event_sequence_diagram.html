เอกสารนี้รวม sequence diagram ของทุก domain event ใน TicketLite แยกตาม domain ที่เป็นเจ้าของ event (producer) โดยแต่ละ diagram แสดงว่า event เกิดจากอะไร ใครฟัง และฟังแล้วทำอะไรต่อ

ข้อตกลงที่ใช้ในทุก diagram:

  • ลูกศรทึบ (->>) คือ call แบบ synchronous เช่น REST, GraphQL หรือ gRPC
  • ลูกศรประ (-->>) คือ response หรือ event ที่ publish ผ่าน message broker
  • ทุก service publish event ผ่าน transactional outbox คือเขียน event ลงตาราง outbox ใน transaction เดียวกับการเปลี่ยน state แล้วให้ relay ส่งเข้า broker ภายหลัง เพื่อไม่ให้ state กับ event หลุดกัน
  • ฝั่งผู้ฟังทุกตัวต้อง idempotent โดยกันการประมวลผลซ้ำด้วย eventId

0. Identity & Access (Keycloak)

Keycloak ไม่มี domain event ของเราเอง แต่ทุก flow เริ่มจากการได้ token มาก่อน diagram นี้จึงแสดงที่มาของ token ที่ใช้ในทุก diagram ถัดไป

sequenceDiagram
    autonumber
    actor U as Customer
    participant P as Mock Partner
    participant GW as APISIX
    participant KC as Keycloak
    participant BFF as GraphQL BFF

    rect rgba(120,120,200,0.08)
    Note over U,KC: Customer ใช้ Authorization Code + PKCE
    U->>GW: GET /auth (redirect)
    GW->>KC: forward ไปหน้า login
    KC-->>U: authorization code
    U->>KC: แลก code เป็น token
    KC-->>U: access token + refresh token
    end

    rect rgba(120,200,120,0.08)
    Note over P,KC: Partner ใช้ Client Credentials
    P->>KC: POST /token (client_id, client_secret)
    KC-->>P: access token พร้อม scopes
    end

    U->>GW: POST /graphql + Bearer token
    GW->>GW: ตรวจ JWT signature, exp, aud และ rate limit
    GW->>BFF: forward พร้อม claims
    BFF->>BFF: ตรวจ role และ field-level authorization

2. Booking

2.1 SeatsHeld และ BookingCreated

sequenceDiagram
    autonumber
    actor U as Customer
    participant BFF as GraphQL BFF
    participant BK as Booking
    participant R as Redis
    participant CAT as Event Catalog
    participant MB as Message Broker
    participant PAY as Payment

    U->>BFF: mutation holdSeats(showtimeId, seatIds)
    BFF->>BK: gRPC HoldSeats
    BK->>BK: ตรวจจำนวนตั๋วต่อ user ต่อรอบ
    BK->>R: Lua script SET NX ทุกที่นั่ง TTL 10 นาที
    alt ได้ครบทุกที่นั่ง
        R-->>BK: OK
        BK-->>MB: SeatsHeld(holdId, expiresAt)
        BK-->>BFF: holdId, expiresAt
    else มีบางที่นั่งถูก hold ไปแล้ว
        R-->>BK: CONFLICT (script rollback ทั้งชุด)
        BK-->>BFF: SEAT_UNAVAILABLE
    end

    U->>BFF: mutation createBooking(holdId)
    BFF->>BK: gRPC CreateBooking
    BK->>R: ตรวจว่า hold ยังอยู่และเป็นของ user นี้
    BK->>CAT: gRPC GetTierPrices(showtimeId)
    CAT-->>BK: ราคาปัจจุบัน
    BK->>BK: snapshot ราคาลง booking<br/>status เป็น AwaitingPayment
    BK-->>MB: BookingCreated(bookingId, amount)
    BK-->>BFF: bookingId
    MB-->>PAY: BookingCreated
    PAY->>PAY: สร้าง Payment (Initiated)<br/>และ PaymentIntent กับ provider
    BFF->>PAY: gRPC GetCheckout(bookingId)
    PAY-->>BFF: checkout URL หรือ client secret
    BFF-->>U: ไปหน้าชำระเงิน

2.3 BookingConfirmed และ TicketsIssued

sequenceDiagram
    autonumber

    MB-->>PA: BookingConfirmed

3. Payment

3.1 รับ webhook จนเป็น PaymentSucceeded

sequenceDiagram
    autonumber
    participant ST as Stripe / Mock Provider
    participant GW as APISIX
    participant PAY as Payment
    participant DB as Payment DB
    participant MB as Message Broker
    participant BK as Booking

    ST->>GW: POST /webhooks/payment
    GW->>GW: IP allowlist, จำกัดขนาด body และ rate limit
    GW->>PAY: forward raw body
    PAY->>PAY: ตรวจ signature กับ timestamp (ACL)
    alt signature ไม่ถูกต้อง
        PAY-->>ST: 400 และบันทึก security log
    else ถูกต้อง
        PAY->>DB: INSERT WebhookEvent(providerEventId)<br/>ON CONFLICT DO NOTHING
        alt เคยรับ event นี้แล้ว
            PAY-->>ST: 200 (ไม่ทำซ้ำ)
        else event ใหม่
            PAY->>PAY: แปลง payload ของ provider เป็น domain model
            PAY->>PAY: ตรวจยอดเงินตรงกับ Payment<br/>status เป็น Succeeded
            PAY->>DB: บันทึก state และ outbox ใน transaction เดียว
            PAY-->>ST: 200
            PAY-->>MB: PaymentSucceeded
            MB-->>BK: PaymentSucceeded
            Note over BK: ดูต่อใน 2.3
        end
    end

4. Notification

Notification ฟังทุก event ที่ต้องแจ้งลูกค้า flow ด้านล่างใช้เหมือนกันกับทุก event

sequenceDiagram
    autonumber
    participant MB as Message Broker
    participant NT as Notification
    participant KC as Keycloak Admin API
    participant SMTP as Email Provider
    participant DLQ as Dead Letter Queue

    MB-->>NT: event ใดๆ เช่น TicketsIssued
    NT->>NT: ตรวจ eventId กันส่งซ้ำ
    NT->>KC: ดึง email จาก userId (cache ใน Redis)
    KC-->>NT: email, locale
    NT->>NT: เลือก template ตาม event และ locale<br/>สร้าง Notification (Queued)
    loop retry สูงสุด 5 ครั้ง (exponential backoff)
        NT->>SMTP: ส่ง email
        alt สำเร็จ
            SMTP-->>NT: 250 OK
            NT->>NT: status เป็น Sent
            NT-->>MB: NotificationSent
        else ล้มเหลว
            SMTP-->>NT: error
            NT->>NT: retryCount เพิ่ม 1
        end
    end
    opt ครบจำนวนครั้งแล้วยังไม่สำเร็จ
        NT->>NT: status เป็น Failed
        NT-->>MB: NotificationFailed
        NT->>DLQ: ส่งไป dead letter
    end

5. Partner Integration

5.1 Partner booking และ AllocationExhausted

booking ของ partner ไม่ผ่าน Payment เพราะ partner เก็บเงินลูกค้าเองแล้วเคลียร์ยอดทีหลัง

sequenceDiagram
    autonumber
    participant P as Mock Partner
    participant GW as APISIX
    participant PA as Partner API
    participant BK as Booking
    participant MB as Message Broker
    participant NT as Notification

    P->>GW: POST /v1/holds
    GW->>PA: forward (JWT, scope booking:write)
    PA->>PA: ตรวจ allocation ของ partner คงเหลือพอ
    PA->>BK: gRPC HoldSeats(channel=PARTNER)
    BK-->>PA: holdId
    PA-->>P: holdId

    P->>GW: POST /v1/bookings + Idempotency-Key
    GW->>PA: forward
    PA->>PA: ตรวจ Idempotency-Key<br/>ถ้า key ซ้ำแต่ body ต่างกัน ตอบ 422
    PA->>PA: เพิ่ม allocation.used แบบ conditional update<br/>(used + n ต้องไม่เกิน quota)
    PA->>BK: gRPC CreatePartnerBooking(holdId, partnerId, externalOrderRef)
    BK->>BK: status เป็น Confirmed ทันที<br/>และออก ticket
    BK-->>MB: BookingConfirmed(channel=PARTNER)
    BK-->>MB: TicketsIssued
    BK-->>PA: bookingId, tickets
    PA-->>P: 201 Created
    opt allocation ใช้ครบแล้ว
        PA-->>MB: AllocationExhausted(partnerId, showtimeId)
        MB-->>NT: AllocationExhausted
        NT->>NT: แจ้ง organizer
    end

5.2 Outbound webhook และ WebhookDeliveryFailed

sequenceDiagram
    autonumber
    participant MB as Message Broker
    participant PA as Partner API
    participant DB as Partner DB
    participant P as Mock Partner

    MB-->>PA: event เช่น EventCancelled หรือ BookingCancelled
    PA->>DB: หา subscription ที่ตรงกับ event type
    PA->>DB: สร้าง WebhookDelivery (Pending) ต่อ subscription
    loop จนสำเร็จ หรือครบ 8 ครั้ง (backoff 1m, 5m, 30m, ...)
        PA->>PA: sign payload ด้วย HMAC-SHA256<br/>header มี timestamp และ deliveryId
        PA->>P: POST {subscription.url} (timeout 5s)
        alt partner ตอบ 2xx
            P-->>PA: 200
            PA->>DB: status เป็น Delivered
        else timeout หรือ non-2xx
            P-->>PA: 500 / timeout
            PA->>DB: attempt เพิ่ม 1 และตั้ง nextRetryAt
        end
    end
    opt ครบจำนวนครั้งแล้ว
        PA->>DB: status เป็น Dead
        PA-->>MB: WebhookDeliveryFailed
    end

จุดที่ควรเขียน test จาก diagram เหล่านี้

  • Race condition ใน 2.1 กับ 5.1: ยิง hold ที่นั่งเดียวกันพร้อมกันหลาย request ต้องมีคนได้แค่คนเดียว และ partner ต้องจองเกินโควตาไม่ได้
  • Late payment ใน 2.3: เงินเข้าหลัง booking expired ต้องจบที่ refund ไม่ใช่ confirm
  • Duplicate event ทุก consumer: ส่ง event เดิมซ้ำต้องไม่เกิดผลซ้ำ
  • Webhook replay ใน 3.1: ส่ง payload เดิมที่ signature ถูกต้องซ้ำ ต้องไม่ประมวลผลซ้ำ และ payload ที่ timestamp เก่าต้องถูกปฏิเสธ
  • IDOR ใน 2.5: user A ยกเลิก booking ของ user B ไม่ได้
  • Double scan ใน 2.6: สแกนตั๋วใบเดียวพร้อมกันสองเครื่อง ต้องผ่านแค่ครั้งเดียว
